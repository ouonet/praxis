# Discover（탐색）

목표가 모호하거나 비전 수준으로 충분히 정의할 수 없는 경우에 사용한다.

**Gate:** 사용자가 확인할 때까지 설계 없음, 코드 없음, 명세 없음.

목표는 모호한 목표를 `design`에 들어갈 수 있는 문제 진술로 변환하는 것이다. 한 번에 하나씩 질문한다.

## 탐색 노트: `docs/discovery/YYYY-MM-DD-<topic>.md`

```markdown
## 목표
<최초의 모호한 목표>

## 가설
- [ ] <가설 A>
- [x] <가설 B> → 검증됨: <증거>
- [~] <가설 C> → 부정됨: <이유>

## 조사 계획
조건부 단계 — 발견에 따라 업데이트. 구축 계획이 아님.
- [x] Phase 1: <무엇을 할 것인가> → <이후 무엇을 결정할 것인가>
- [ ] Phase 2: <무엇을 할 것인가> (범위는 Phase 1에 의해 결정)

## 실험
### YYYY-MM-DD — <실험 이름>
what: <무엇을 했는가>
saw:  <무엇을 관찰했는가>
conclusion: <무엇을 의미하는가>

## 확정된 방향
<다음 중 하나>
- 문제 진술: 누가 / 어떤 문제 / 어떤 맥락 / 성공 신호
- 지식 명세: 확인된 데이터 구조, 프로토콜 또는 시스템 동작

## 부정된 아이디어
- <아이디어> — <왜 제외했는가>
```

탐색 노트는 세션을 넘어 축적된다. 시작 전에 기존 노트를 확인한다.

## 스파이크 코드: `spikes/YYYY-MM-DD-<topic>/`

스파이크 코드는 가설을 검증하는 것이지, 기능이 아니다.

- 각 스파이크에는 어떤 가설을 테스트하는지 설명하는 `README.md`가 있다.
- 테스트가 필요 없다.
- 메인 코드 경로에 결합하지 않는다.
- 탐색이 끝나면 삭제한다 (배운 것은 노트에 있다).
- 스파이크 코드를 보존할 가치가 있다면 `design → plan → tdd`를 거쳐야 한다 — 직접 승격 불가.

## Gate

`docs/discovery/YYYY-MM-DD-<topic>.md`가 존재하고 "확정된 방향"이 채워져 있을 것.

그 후 사용자와 출구를 선택:

- **→ design**: 방향이 해결해야 할 문제 — `design`에 인계하고 탐색 노트 참조.
- **→ archive**: 방향이 지식 산출물 (역공학 발견, 프로토콜 명세, 데이터 구조 다이어그램) — `docs/discovery/<topic>-spec.md`로 저장, 설계 불필요.

## Abandon（중단）

사용자가 계속하지 않기로 결정한 경우:

1. 탐색 노트에 추가:
   ```
   ## Abandoned — YYYY-MM-DD
   reason: <이유>
   validated: <무엇을 확인했는가>
   invalidated: <무엇이 제외됐는가>
   ```
2. `spikes/<topic>/` 삭제 — 배운 것은 노트에 있다.
3. staging spec, plan, ship 불필요.
4. 탐색 노트는 기록으로 `docs/discovery/`에 영구적으로 보존.
