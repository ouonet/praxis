# Discover（探索）

目標が曖昧または漠然としていて、十分に定義できない場合に使う。

**Gate：** ユーザーが確認するまで、設計なし、コードなし、仕様なし。

目標は、曖昧なゴールを `design` に入れるのに十分な問題陳述に変換することだ。一度に一つずつ質問する。

## 探索ノート：`docs/discovery/YYYY-MM-DD-<topic>.md`

```markdown
## ゴール
<最初の曖昧なゴール>

## 仮説
- [ ] <仮説A>
- [x] <仮説B> → 検証済み：<証拠>
- [~] <仮説C> → 否定済み：<理由>

## 調査計画
条件付きステップ — 発見に応じて更新する。構築計画ではない。
- [x] Phase 1: <何をするか> → <その後何を決定するか>
- [ ] Phase 2: <何をするか> (スコープはPhase 1で決まる)

## 実験
### YYYY-MM-DD — <実験名>
what: <何をしたか>
saw:  <何を観察したか>
conclusion: <何を意味するか>

## 確定した方向
<以下のいずれか>
- 問題陳述：誰 / 何の問題 / どんなコンテキスト / 成功シグナル
- 知識仕様：確認済みのデータ構造、プロトコル、またはシステム動作

## 否定されたアイデア
- <アイデア> — <なぜ除外したか>
```

探索ノートはセッションをまたいで蓄積される。開始前に既存のノートを確認する。

## スパイクコード：`spikes/YYYY-MM-DD-<topic>/`

スパイクコードは仮説を検証するもので、機能ではない。

- 各スパイクには、どの仮説をテストしているかを説明する `README.md` がある。
- テストは不要。
- メインコードパスに結合しない。
- 探索終了時に削除する（学んだことはノートに）。
- スパイクコードを保持する価値があるなら、`design → plan → tdd` を経由しなければならない — 直接昇格できない。

## Gate

`docs/discovery/YYYY-MM-DD-<topic>.md` が存在し、「確定した方向」が埋まっていること。

その後、ユーザーと出口を選択：

- **→ design**：方向が解決すべき問題 — `design` に引き渡し、探索ノートを参照。
- **→ archive**：方向が知識成果物（リバースエンジニアリング発見、プロトコル仕様、データ構造図）— `docs/discovery/<topic>-spec.md` として保存、設計は不要。

## Abandon（中止）

ユーザーが続けないことを決めた場合：

1. 探索ノートに追記：
   ```
   ## Abandoned — YYYY-MM-DD
   reason: <なぜ>
   validated: <何を確認したか>
   invalidated: <何が除外されたか>
   ```
2. `spikes/<topic>/` を削除 — 学んだことはノートに。
3. staging spec、plan、shipは不要。
4. 探索ノートは記録として `docs/discovery/` に永続的に保持する。
